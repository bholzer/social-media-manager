# Codebase Concerns

**Analysis Date:** 2026-03-11

## Security Considerations

**Hardcoded Default Secret Key:**
- Risk: The default JWT secret key in `src/smm/config.py` is set to `"change-me-to-a-random-secret-key"`. If deployed without overriding this via environment variable, tokens can be forged by anyone who reads the code.
- Files: `src/smm/config.py` (line 8), `.env` file, `Dockerfile`
- Current mitigation: Pydantic Settings loads from `.env` file, so it can be overridden. However, this is a common misconfiguration risk in early-stage projects.
- Recommendations: Add startup validation that raises an error if SECRET_KEY is still the default in production. Add to deployment checklist and CI/CD to prevent accidental deployments with default secrets.

**OAuth State Token Storage (In-Memory Dictionary):**
- Risk: OAuth state tokens are stored in a plain Python dict at module level in `src/smm/api/v1/oauth.py` (line 26). This is not persisted across process restarts, leaks memory (no cleanup of old states), and is vulnerable to race conditions in multi-process deployments.
- Files: `src/smm/api/v1/oauth.py` (lines 24-26, 70)
- Current mitigation: 10-minute expiration check (lines 77-83) prevents indefinite replay, but only per process.
- Recommendations: Move state storage to Redis (already in stack) or database with TTL. Implement atomic cleanup of expired states. Document that app must run as single process until fixed.

**Access Tokens Sent as URL Query Parameters:**
- Risk: Facebook access tokens are passed as query parameters in HTTP GET requests in `src/smm/adapters/facebook.py` (lines 34-35) and `src/smm/services/facebook_oauth.py` (lines 87-89). Query parameters are logged by proxies, load balancers, and server logs, compromising token security.
- Files: `src/smm/adapters/facebook.py` (lines 34-35), `src/smm/services/facebook_oauth.py` (lines 87-89)
- Current mitigation: None.
- Recommendations: Use POST requests with request body for sensitive data, or convert to Bearer token headers. Check httpx documentation for request body support in validation endpoints.

**Plaintext Token Storage in Database:**
- Risk: Access tokens (including long-lived Facebook page tokens) are stored unencrypted in `social_accounts.access_token` column (`src/smm/models/social_account.py` line 27). A database breach exposes all user social media accounts.
- Files: `src/smm/models/social_account.py` (lines 27-28), `src/smm/api/v1/oauth.py` (lines 122, 188), `src/smm/api/v1/social_accounts.py`
- Current mitigation: Database access is restricted to the app, but there's no encryption layer or key rotation.
- Recommendations: Implement token encryption at-rest using `cryptography.fernet` or similar. Store encryption key in secure vault (AWS Secrets Manager, HashiCorp Vault). Plan key rotation strategy.

**Missing API Authentication on OAuth Callback:**
- Risk: The `GET /api/v1/oauth/facebook/callback` endpoint (`src/smm/api/v1/oauth.py` lines 59-143) does not require authentication. An attacker can redirect a user to the callback endpoint with arbitrary `code` and `state` parameters to trigger Facebook API calls on behalf of the app (SSRF/abuse potential).
- Files: `src/smm/api/v1/oauth.py` (lines 59-143)
- Current mitigation: State validation mitigates some attacks, but only if the state was generated by an authenticated user.
- Recommendations: Require that callback is called only after a recent `/facebook/connect` call from an authenticated user. Use signed/encrypted state tokens that encode user_id, not just a random string.

**Sensitive Data in Error Messages:**
- Risk: Error messages in routes expose implementation details. For example, `src/smm/api/v1/auth.py` line 29-31 logs exceptions with full stack traces to logger. Facebook exceptions propagate raw error messages to clients (`src/smm/api/v1/oauth.py` lines 95-97, 103-106).
- Files: `src/smm/api/v1/auth.py` (line 28), `src/smm/api/v1/oauth.py` (lines 95-97, 103-106, 114-116), `src/smm/api/v1/posts.py`
- Current mitigation: HTTPException converts to generic 502 for some errors, but raw messages may still leak.
- Recommendations: Create standardized error response handling. Log full errors server-side; return generic messages to clients. Use correlation IDs to link client errors to server logs.

## Tech Debt

**Shared Adapter Instances (Thread Safety):**
- Issue: Platform adapters in `src/smm/adapters/registry.py` (lines 8-11) are instantiated once at module load time and reused. If adapters hold state (e.g., connection pools, rate limiters), this could cause issues in concurrent requests. Currently FacebookAdapter creates new httpx.AsyncClient per request, which is correct, but this pattern is fragile if adapters are later optimized to pool connections.
- Files: `src/smm/adapters/registry.py`, `src/smm/adapters/facebook.py` (lines 22-23), `src/smm/adapters/instagram.py`
- Fix approach: Document that adapters must be stateless. Add a note in `AbstractPlatformAdapter` docstring. If pooling is added, switch to per-request adapter instantiation via a factory method.

**Dramatiq Worker Blocking on asyncio.run():**
- Issue: Dramatiq actor `publish_target_task` in `src/smm/workers/tasks.py` (lines 10-11) calls `asyncio.run()` to bridge sync Dramatiq to async code. This blocks the worker thread and can cause deadlocks if multiple tasks try to create event loops. asyncio.run() is also slow (creates/destroys event loop each invocation).
- Files: `src/smm/workers/tasks.py` (lines 10-11)
- Fix approach: Replace Dramatiq with an async task queue (Celery with gevent, or switch to a Python-native async queue like `RQ-Async` or `Taskiq`). Alternatively, use a shared event loop manager or `nest_asyncio` (not recommended for production).

**APScheduler Poll Interval Hardcoded:**
- Issue: The scheduler polls every 30 seconds (line 51 in `src/smm/scheduler/scheduler.py`), which is not configurable. This is a trade-off between latency (lower = faster publish) and database load. No way to tune without code change.
- Files: `src/smm/scheduler/scheduler.py` (line 51)
- Fix approach: Move poll interval to config (`settings.scheduler_poll_interval_seconds`). Add documentation of impact on latency vs. load.

**No Request Logging/Tracing:**
- Issue: No middleware or instrumentation logs HTTP requests, response times, or errors. Makes debugging production issues difficult. Traces from worker to scheduler are also missing.
- Files: `src/smm/main.py`
- Fix approach: Add `RequestLoggingMiddleware` to FastAPI app. Use `structlog` for structured logging. Add correlation IDs to trace requests across components.

**Unvalidated Facebook API Responses:**
- Issue: Facebook API responses are parsed without checking required fields. For example, `src/smm/services/facebook_oauth.py` line 94-97 assumes `p["id"]` and `p["name"]` exist; `src/smm/services/facebook_oauth.py` line 121 assumes `profile["id"]` exists. Missing fields will raise KeyError without clear error messages.
- Files: `src/smm/services/facebook_oauth.py` (lines 92-99, 102-110)
- Fix approach: Add Pydantic models for Facebook API responses. Validate before using. Handle missing fields gracefully.

## Test Coverage Gaps

**No Integration Tests for Scheduler:**
- What's not tested: The scheduler `start_scheduler()` and `stop_scheduler()` functions (`src/smm/scheduler/scheduler.py` lines 49-59) are not tested end-to-end. The test in `tests/integration/test_scheduler.py` mocks the database session and task queue, so it doesn't verify the scheduler actually runs on a background thread or respect start/stop lifecycle.
- Files: `src/smm/scheduler/scheduler.py`, `tests/integration/test_scheduler.py`
- Risk: Scheduler could fail silently at startup. Race conditions between scheduler thread and main app thread are not detected.
- Priority: High

**No Tests for Adapter Token Validation:**
- What's not tested: `validate_token()` method in adapters is never called in tests. No verification that revoked/expired tokens are properly rejected.
- Files: `src/smm/adapters/facebook.py` (lines 32-36), `src/smm/adapters/instagram.py`
- Risk: An expired token stored in the database will only fail when actual publish is attempted, causing post failure instead of early detection.
- Priority: Medium

**No E2E Test for Full Publishing Pipeline:**
- What's not tested: The file `tests/e2e/test_publish_flow.py` exists but no content is visible. The full pipeline (schedule post → scheduler picks up → enqueue task → worker publishes) is untested.
- Files: `tests/e2e/test_publish_flow.py`
- Risk: Race conditions and timing issues in the two-layer publish system could only be found in production.
- Priority: High

**No Tests for OAuth State Expiration:**
- What's not tested: OAuth state cleanup and expiration edge cases. No test for clock skew, concurrent callback attempts, or state token replay.
- Files: `src/smm/api/v1/oauth.py` (lines 70-143), `tests/integration/test_oauth.py`
- Risk: OAuth state leaks memory indefinitely in production; replay attacks possible in edge cases.
- Priority: Medium

**No Tests for Error Handling in Adapters:**
- What's not tested: What happens when Facebook API returns non-JSON response, network timeout, rate limiting (429), or invalid credentials. Only happy path is tested.
- Files: `src/smm/adapters/facebook.py` (lines 9-30), `tests/unit/test_adapters.py`
- Risk: Unhandled exceptions cause worker to crash or stuck. Poor error messages.
- Priority: Medium

**No Tests for Database Constraints:**
- What's not tested: Cascading deletes (user delete → posts/accounts delete), foreign key integrity, unique constraints on (user_id, platform, platform_user_id).
- Files: `src/smm/models/` (all files)
- Risk: Data integrity issues only caught in production.
- Priority: Low (SQLAlchemy and PostgreSQL enforces these, but explicit tests would catch ORM bugs)

## Fragile Areas

**Post Publish Endpoint (Manual Trigger):**
- Files: `src/smm/api/v1/posts.py` (lines 93-133)
- Why fragile: The `/posts/{post_id}/publish-now` endpoint sets targets to PUBLISHING and enqueues tasks. If any target is already PUBLISHING, it's silently skipped (lines 108-111). If enqueueing fails partially, the transaction is committed but some targets never publish. No retry logic.
- Safe modification: Add tests for all edge cases. Consider using a distributed transaction or saga pattern. Add logging of each enqueue.

**Scheduler Poll Query:**
- Files: `src/smm/scheduler/scheduler.py` (lines 23-29)
- Why fragile: The query fetches all targets matching `status=SCHEDULED AND scheduled_at <= now()`. Under high load, this could be slow or cause database contention. No index hint or pagination.
- Safe modification: Verify index on `(status, scheduled_at)` exists. Add LIMIT clause to prevent loading all targets at once. Monitor query performance.

**OAuth Callback Error Paths:**
- Files: `src/smm/api/v1/oauth.py` (lines 59-143)
- Why fragile: Multiple external API calls (exchange_code, get_long_lived_token, get_user_pages, get_user_profile) can fail. Each failure path returns a different error. No retry logic or circuit breaker. If Facebook is down, all OAuth flows fail.
- Safe modification: Add timeout parameters to httpx calls. Implement exponential backoff for transient errors. Add fallback for missing user pages (already done on line 108, but document it).

**PostTarget Status Transitions:**
- Files: `src/smm/services/post.py` (lines 105-106, 112-124), `src/smm/api/v1/posts.py` (lines 107-111)
- Why fragile: Status can transition in multiple places (scheduler, publish endpoint, worker). No validation of allowed transitions. Example: a PUBLISHED target being reverted to DRAFT by an update call that checks `scheduled_at`. This can cause posts to be republished.
- Safe modification: Add explicit state machine (allowed transitions). Use a dedicated `update_status()` method that enforces rules. Add audit trail.

## Performance Bottlenecks

**Scheduler Query + Enqueue Pattern:**
- Problem: Scheduler runs every 30 seconds, fetches all due targets, transitions them to PUBLISHING in a single transaction, then enqueues each one. If there are 1000 due targets, this causes 1000 sequential Dramatiq.send() calls (one per loop iteration on line 46 in scheduler.py). Each send may hit Redis.
- Files: `src/smm/scheduler/scheduler.py` (lines 14-46)
- Cause: No batching of task enqueueing. Redis is fast but still not free.
- Improvement path: Batch enqueue calls. Dramatiq supports `send_batch()`. This would reduce Redis round trips from N to 1.

**No Database Connection Pooling Configuration:**
- Problem: SQLAlchemy async engine is created with default pool settings (QueuePool, max_size=5). Under load, connections may exhaust, causing request queuing.
- Files: `src/smm/database.py` (line 7)
- Cause: Default pool is conservative (5 connections for a single-process app is low).
- Improvement path: Add configurable pool_size and max_overflow. Monitor in staging. Typical web app needs pool_size = (num_workers * 2).

**No Database Query Optimization:**
- Problem: `PostService.list()` in `src/smm/services/post.py` (lines 65-95) uses `selectinload()` to eager-load targets, but then calls `.unique()` on the result (line 90). This is slow pattern when posts have many targets (N+1 adjacent issue after join).
- Files: `src/smm/services/post.py` (line 90)
- Cause: Eager loading with join duplicates rows; `.unique()` deduplicates in Python instead of SQL.
- Improvement path: Use `contains_eager()` instead of `selectinload()`. This loads relationships in a single query via careful JOIN.

**Facebook API Calls Not Cached:**
- Problem: Every publish target calls Facebook API to post content. There's no caching of tokens, rate limit handling, or batching of posts.
- Files: `src/smm/adapters/facebook.py` (lines 9-30), `src/smm/services/publisher.py` (lines 32-38)
- Cause: Current design is simple but doesn't scale. Facebook has rate limits (typically 1000 calls/day per app).
- Improvement path: Implement rate limiting with sliding window counter. Cache token validation results. Implement batch endpoint (Facebook Graph Batch API).

**No Async Connection Reuse in Adapters:**
- Problem: Each publish call creates a new `httpx.AsyncClient()` (line 22 in facebook.py). This destroys and recreates the connection after each request.
- Files: `src/smm/adapters/facebook.py` (lines 22-23)
- Cause: Safest approach for a singleton adapter, but not most efficient.
- Improvement path: Switch to per-request adapter factory (mentioned in Tech Debt section above) and reuse client via context manager or app state.

## Scaling Limits

**Single APScheduler Thread:**
- Current capacity: One instance of scheduler can poll and enqueue for one app instance. If app is scaled to 2+ instances, scheduler runs on all of them, causing duplicate task enqueueing (same target enqueued multiple times).
- Limit: Breaks at 2+ concurrent app instances.
- Scaling path: Use a distributed scheduler (Celery Beat, APScheduler with persistent storage). Lock-based approach: only one instance acquires a lock to run the poll job.

**OAuth State Storage:**
- Current capacity: Unlimited (dict grows without bound). Memory usage = O(num_pending_oauth_flows).
- Limit: Server restart wipes all pending flows; high memory usage if flows accumulate (10MB+ for 1M flows).
- Scaling path: Move to Redis. Implement TTL-based cleanup.

**In-Memory Dramatiq Task Queue (Redis Default):**
- Current capacity: Limited by Redis memory. Typical deployments: 6GB → ~100M small tasks.
- Limit: Tasks overflow after RAM limit. No persistence unless RDB/AOF enabled.
- Scaling path: Already using Redis Broker, so this is handled at Redis layer. Monitor Redis memory and configure persistence.

**Database Single Instance (PostgreSQL):**
- Current capacity: Typical small instance (2 CPU, 4GB RAM) handles ~100 concurrent connections, ~1000 req/sec.
- Limit: Write bottleneck at single-server scale. No replication or failover in current setup.
- Scaling path: Add read replicas for analytics queries. Implement sharding if dataset grows. Add pgbouncer for connection pooling at app tier.

## Dependencies at Risk

**python-jose (JWT Library):**
- Risk: `python-jose` is less actively maintained than `PyJWT`. Version in pyproject.toml is `python-jose[cryptography]>=3.3.0` (open-ended).
- Impact: Security updates may lag. If a JWT vulnerability is found, may not be patched quickly.
- Migration plan: Monitor GitHub for security issues. If activity drops further, migrate to `PyJWT` (same API mostly).

**Dramatiq (Task Queue):**
- Risk: Dramatiq is less popular than Celery, Huey, or RQ. Smaller community, slower updates.
- Impact: Fewer integrations, slower debugging, edge cases may not be fixed.
- Migration plan: If issues arise, switch to `Celery` with RabbitMQ or Redis backend. Moderate effort (~2 days refactor). API is similar.

**APScheduler (Scheduling):**
- Risk: APScheduler is widely used but in-memory background scheduler is not suitable for production at scale (no persistence, no HA).
- Impact: Scheduler is a SPOF. If app restarts, scheduled jobs are lost.
- Migration plan: Migrate to Celery Beat (distributed scheduler) or move to dedicated cronjob (Kubernetes CronJob). No-code path: add a persistent job store to APScheduler (PostgreSQL adapter).

## Missing Critical Features

**Token Refresh / Expiration Handling:**
- Problem: Social account tokens expire. There's a `token_expires_at` column in `src/smm/models/social_account.py` (line 29), but no code refreshes tokens. When a token expires, publish will silently fail with a generic "API error".
- Blocks: Long-running scheduled posts (> 60 days).
- Fix: Implement token refresh on-demand before publish, or background refresh job before expiration.

**Retry Logic for Failed Publishes:**
- Problem: When a publish fails, it's marked as FAILED with an error message. There's no UI to retry, no automatic retry with backoff, no way to recover without manual DB intervention.
- Blocks: Transient failures (network hiccup, rate limit) cause permanent failure.
- Fix: Add retry count and last_error_at timestamp. Implement exponential backoff retry job. Add UI to manually retry.

**Multi-Platform Publishing (Partial):**
- Problem: Adapters are registered for TWITTER and LINKEDIN (in Platform enum in `src/smm/models/social_account.py` lines 15-16), but no adapters implemented. Trying to publish to these platforms raises ValueError.
- Blocks: Twitter and LinkedIn integration.
- Fix: Implement adapters or remove from Platform enum to avoid confusion.

**Rate Limiting:**
- Problem: No rate limiting on API endpoints. A user can spam requests (e.g., create 1000 posts instantly, publish to 1000 platforms). This could cause DOS on social media APIs.
- Blocks: API abuse prevention.
- Fix: Add Slowapi or similar FastAPI middleware for rate limiting. Configure limits per endpoint.

**Audit Trail:**
- Problem: No audit log for who created/modified/published posts or connected accounts. Makes it hard to debug issues or enforce compliance.
- Blocks: Compliance, security investigation, user support.
- Fix: Add created_by, updated_by, and action audit log table. Log all sensitive changes.

**Webhook for Long-Running Operations:**
- Problem: Publish is fully async (scheduled/background). There's no way for frontend to know when publish completed without polling. Client must repeatedly GET /posts/{id} to check status.
- Blocks: Real-time UI updates.
- Fix: Add WebSocket support or server-sent events (SSE) to notify clients of status changes. Alternatively, provide a webhook callback URL in the API.
